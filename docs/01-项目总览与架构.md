# 01 项目总览与架构

## 1. 背景

公司在做一套 AI 驱动的销售/获客系统（`main` 大系统），其中：

- **Twenty CRM**：业务数据中枢（客户/线索/商机/跟进等）。
- **lead platform**：业务编排层（决定查谁、何时查重/查海关、领到哪个账号、何时建档/跟进/释放，并协调 CRM、飞鸽外呼、Agent）。
- **fuma-platform（本项目）**：孚盟（fumamx.com）的**薄封装层/上游适配器**。
- 其他同族客户端（tanji-client、boss-client、feige-outbound-platform 等）负责各自上游。

**为什么需要 fuma-platform**：孚盟是公司的**客保库**（客户保护/归属的事实所在）+ **海关数据源**。
公司现有 N 个真实业务员账号（3–50 个），每个账号默认 500 个保护客户容量（实际上限按上游角色规则解析，实测 300/200/500 三档）。
平台要把这些账号的「客保能力」和「海关数据能力」变成可编程、可并发、可观测的本地服务，供 lead platform 编排与调用。

## 2. 定位与边界

### 2.1 做什么（薄封装，忠实映射上游）

- 多账号会话管理：登录（钉钉扫码 SSO 主路径；账密+滑块+钉钉验证备选）、token 持久化与保活、失效重登。
- 客户管理（客保）：客户列表/详情/建档/编辑、公海（列表/领取/释放）、联系人、跟进记录、保护状态。
- 客户查重：单条/批量（≤200）、查重历史、结果本地快照与定期复核。
- 海关数据：贸易大数据查询（按公司/按产品/按数据源/交易分析）、贸易监测。
- 请求池：把查询类任务分摊到多个账号，做并发、限流、去重、重试。
- 任务化：批量任务异步执行（taskId + 状态 + 结果 + 取消）。
- 本地事实与同步：本地先落事实 → outbox 异步同步上游；上游规则变化对账回流。
- 事件：本地状态变更发布事件（供 lead platform / 其他系统订阅）。
- 四入口：CLI / REST / MCP / SKILL 同一套能力。

### 2.2 不做什么

- ❌ **不做业务编排**：不决定查谁、领谁、何时建档/跟进/释放（那是 lead platform 的职责）。
- ❌ 不封装孚盟其他模块：线索/商机、邮件/询盘、营销、报价/订单/单证、采购/库存/财务、沟通/WhatsApp、知识库、报表等。
- ❌ 不直接对接 lead platform/Twenty CRM 的具体业务流程（外部系统交互"封装好即可"，后续再定义）。
- ❌ 不做跨系统决策、不做线索评分、不做自动营销。

## 5. 关键设计约束（来自需求方）

1. **账号 = 真实业务员账号**，平台建好后真人不再操作该账号；平台是唯一操作者。
2. **写操作必须显式传 `accountId`**（调用方指定），平台只做校验与执行，不替调用方选账号。
3. 账号规模按 **3–50** 设计；单账号保护客户默认上限 **500**（实际以「角色→custLimit 规则」解析为准，实测 300/200/500）。
4. 上游风控强度、调用频率上限**未知** → 默认保守：账号级限速、退避、熔断、告警。
5. **本地优先**：本地先成为事实 → outbox 异步同步上游；冲突最终收敛到上游（已确认，见 00 §5 / 05 v4）。
6. **批量任务任务化**：持久化任务、状态机、并发度、重试、取消、结果查询。
7. 登录目标：**扫码为主**（CLI 终端渲染 / REST Base64），二维码需**解码后重新编码渲染**；账密+滑块+钉钉验证作为备用模式。
8. 技术栈沿用同族项目：TypeScript + Node 22 + cloakbrowser（共享 `~/cloak-env`）+ SQLite + CLI/REST/MCP/SKILL + systemd 常驻 + spec 自动生成。
9. 外部系统交互"封装好即可"：事件/API 先定义清楚，具体消费方后续接入。

## 6. 核心数据流

### 6.1 登录
```
触发登录(账号) → 打开孚盟登录页 → 点击「钉钉扫码登录」
→ 钉钉 OAuth 弹窗二维码 canvas → 解码 payload → 重新编码渲染(CLI/REST)
→ 人工扫码确认 → 自动选钉钉组织 → 回调孚盟 → 自动选企业/进入企业
→ 工作台加载 → 采集 tokens → 加密持久化 → 会话在线
```

### 6.2 读（列表/详情/查重/海关）
```
调用方 → 能力层 → 本地缓存/快照命中？
  是 → 返回（带 stale 标识）
  否 → RequestPool(选账号) → 上游 HTTP → 校验 → 写本地 → 返回
```

### 6.3 写（本地优先）
```
调用方(指定 accountId) → 本地校验（容量/冷却/规则/权限）
→ 本地事务落库 + 写 outbox + 发事件（status=pending）
→ 异步 worker 推上游 → 成功：本地状态 synced + 事件
                       → 失败：重试/告警/回滚策略
```

### 6.4 批量（任务化）
```
调用方 → 创建 task（类型、参数、账号/池、并发度）
→ 后台执行（RequestPool）→ 进度/结果持久化
→ 调用方轮询 task 状态（或后续 webhook）
```

### 6.5 对账
```
定时/触发 → 拉上游增量（客户/公海/跟进/容量）
→ diff 本地 → 吸收上游事实（保护到期/被领取/掉公海等）
→ 更新本地 + 发事件 + 记录差异
```

## 7. 技术选型（建议，待 P1 确认）

| 项 | 选择 | 理由 |

# 附：v2 增补（2026-11-14 现场抓包后）

## A. 容量与并发估算（3–50 账号）

| 项 | 数值/公式 | 说明 |
|---|---|---|
| 客保容量 | 账号数 × 实际上限（默认 500） | 3 账号≈1,500；50 账号≈25,000；实际上限按角色规则（实测 300/200/500） |
| 公海池 | 379,597（实测） | 全公司共享，领取竞争 |
| 客户查询 | 单账号 2 QPS 读 | 50 账号理论 100 QPS，实际受上游风控限制应远低于此 |
| 查重/海关查询 | 受账号数与限速约束 | 请求池并发 ≈ 在线账号数 × 每账号并发(1–2) |
| token 生命周期 | 24h 硬上限（实测） | 每天需重登；靠心跳/免扫码实验优化 |
| SQLite 规模 | 客户 ≤2.5 万 + 跟进/联系人/事件 | 单机 SQLite WAL 足够 |

## B. 部署拓扑（建议）

```
单机 NixOS/systemd user service
├── fuma-platform daemon（Node 22 单进程）
│   ├── SQLite（~/.fuma-platform/data/fuma.db，WAL）
│   ├── REST 127.0.0.1:17890
│   ├── MCP stdio（由宿主按需拉起）
│   └── 登录用浏览器（cloakbrowser，仅在登录/重登/刷新二维码时拉起；每账号独立 profile）
└── 日志 ~/.fuma-platform/logs（JSONL，轮转/脱敏）
```

**关键决策**：
1. 业务调用走 Node HTTP（已实测可行），浏览器**只在登录链路使用** → 50 账号常驻内存可控。
2. 本地优先 + outbox：写请求不阻塞在上游；上游失败不影响本地事实可用。
3. 规则引擎内建 15/3/500 不变式，读上游配置为准（读不到用默认值并标注来源）。
4. 事件总线先 outbox + 轮询/webhook，不绑定消费方。
5. 四入口由单一 spec 生成，避免契约漂移。

## C. 关键设计取舍

| 决策 | 选择 | 放弃的方案及原因 |
|---|---|---|
| 登录方式 | 钉钉 SSO 扫码为主 | 纯账密：受腾讯滑块+钉钉验证+短信通道限制，稳定性差 |
| 会话恢复 | token 持久化（加密）+ 需要时重登 | 浏览器会话持久化：实测 SPA 状态无法跨进程恢复（nopage） |
| 数据一致性 | 本地优先 + 对账 | 上游优先：写入受上游可用性/规则限制，无法满足编排实时性 |
| 列表读取 | 本地缓存 + 可强制刷新 | 全量实时：上游限速/延迟不可控 |
| 请求调度 | 账号池 + 请求池 | 单账号串行：3–50 账号下吞吐浪费 |
| 批量任务 | 持久化任务化 | 同步长请求：易超时/不可恢复 |
