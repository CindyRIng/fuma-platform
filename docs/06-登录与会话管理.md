# 06 登录与会话管理（v2）：快速自动登录 + 长期保活

> 目标：**登录尽可能快、重登尽量免人工、会话长期在线**。全部基于 P0 实测事实设计。
> 状态：设计文档 v4（未实现；v3/v4 附录含实测与保活结论）。

## 1. 事实基础（P0 已验证）

| 事实 | 结论 |
|---|---|
| 主登录方式 | 钉钉 SSO 扫码（孚盟登录页「钉钉」入口） |
| 扫码必须人工 | 首次/新设备需手机钉钉扫码确认；二维码有效期短（约 60s） |
| 登录后 token | `accessToken` + `individualAccessToken`，**24h 后过期**，无 refresh 接口（bundle 未见） |
| 业务调用 | 带 token 直接 HTTP 即可，**不需要浏览器**（已验证客户/公海/查重/海关/监测） |
| 浏览器态 | SPA 启动强依赖会话态：**关闭浏览器进程后无法仅靠 cookies+storage 恢复**（实测注入失败，跳 `#/main/nopage`） |
| 钉钉侧会话 | OAuth 页有「自动登录」勾选；登录后存在 `stayLogin/account/deviceid/pub_uid/pub_org_id/tfstk` 等 DingTalk cookie/localStorage |
| 二维码 | 钉钉定制样式，需 ZXing 解码后自行重编码渲染 |
| 组织/企业选择 | 钉钉组织列表精确选择 + 孚盟企业列表选择，均可自动化 |

## 2. 登录模式与状态机

模式：`dingtalk_sso_qr`（主）、`password_slider_dingtalk`（备）、`manual_token`（应急）。

```
idle
 → prewarm            (预启动浏览器/预加载登录页，常驻)
 → starting           (点击钉钉入口)
 → qr_ready           (二维码已解码+重编码)
 → scanned            (11041)
 → confirmed          (success: chooseOrganization)
 → org_selected       (精确选钉钉组织)
 → redirected         (thirdPartyAuthSuccess)
 → enterprise_selected(选企业+进入)
 → online             (tokens 加密落库)
异常 → failed / expired / cancelled / manual_required
```

事件：`session.login.*`、`session.state.changed`、`session.qr.ready`、`session.expired`。

## 3. 「快」的设计

### 3.1 预启动（prewarm）与常驻页面

- daemon 启动后按需创建**登录专用浏览器上下文**（cloakbrowser，独立 profile/账号），并预加载：
  - `https://www.fumamx.com/#/login`（登录页资源缓存）
  - 登录会话期间保持该页面（不关闭），触发登录时直接点击「钉钉」入口，节省页面加载时间；注意：这是登录流程内复用，不代表 daemon 常驻浏览器（默认不常驻，见 v4 结论）。
- 加载资源（`cdnstatic`/字体）可被 HTTP 缓存复用（浏览器 profile 持久化）。
- 预估：页面冷启动 ~6-9s；预启动后到「钉钉弹窗打开」< 1.5s。

### 3.2 登录流程加速点

1. **并行准备**：点击钉钉图标后立即等待 popup；同时注册 `login_with_qr` 响应监听；二维码 canvas 出现即取图，不等页面 idle。
2. **轮询提速**：不使用固定 sleep；以 `login_with_qr` 的响应（11021→11041→success）作为状态机驱动；页面自身轮询约 5s 一次，平台只需监听网络事件（Playwright response 事件延迟约 <100ms）。
3. **组织选择自动化**：`orgList` 到手后立即用精确名称点击（避免等页面渲染完成再找）；点击后监听跳转。
4. **企业选择自动化**：回跳后立即轮询「选择您要进入的企业」DOM（每 300ms），出现即选企业+点「进入」。
5. **token 采集前置**：工作台启动时并行监听 `sessionStorage`（accessToken 一出现即采集落库），不用等页面完全加载。
6. **失败快速重试**：二维码失效 → 立即 `popup.reload()` 重新生成（<2s），不等待人工。

### 3.3 免扫码重登（关键优化，需 P2 实验验证）

**假设**：首次扫码后，DingTalk 会话（stayLogin/deviceid 等）与浏览器 profile 保留；在 DingTalk 会话有效期内再次打开 OAuth 页面，可能**直接进入组织选择/授权页**（甚至自动确认），无需重新扫码。

**验证方案（P2 首日）**：
1. 完成一次扫码登录，保留 profile 不删。
2. 关闭页面，重新打开登录页→钉钉 OAuth 页，观察：
   - 是否直接显示组织列表（已登录态）？
   - 是否出现「自动登录」勾选项且默认勾选？
   - 网络是否自动触发 login_with_qr success（无扫码）？
3. 若可免扫码 → 实现 `silentRelogin`：token 临期时用同 profile 重走 OAuth，全自动获取新 token（目标 <15s）。
4. 若不可 → 退化为「预启动 + 二维码快速下发 + 人工扫码」（目标：二维码出现 <5s，确认后 <8s 上线）。

**其他加速候选（需实验）**：
- DingTalk OAuth 页面「账号登录」：手机号+密码后若命中可信设备，可能仅需一次确认（免扫码），但受短信/风控影响。
- 复用 `authCode`/`codeForToken`：authCode 一次有效，不能复用。
- 是否有隐藏 token 刷新接口：bundle 未见；P2 用浏览器抓包观察 token 到期前页面是否静默续期（例如 `personalsettingGet` 心跳是否延长 expireTime）。

### 3.4 性能预算（验收指标）

| 场景 | 目标 |
|---|---|
| daemon 已预启动 → 二维码就绪（qr_ready） | ≤ 5s |
| 用户扫码确认 → online（token 落库） | ≤ 8s |
| 免扫码重登（如可行） | ≤ 15s/账号 |
| 多账号并行登录 | 并发 ≤2，互不阻塞 |
| 登录失败可诊断 | 每步状态/截图/错误码可查 |

## 4. 「长期保活」的设计

### 4.1 心跳与健康度

- 每账号心跳：每 3–5min 调 `GET /pcapi/UniversalInterface/personalsettingGet`（轻量只读，已验证）。
- 记录：延迟、错误码、连续失败数、token 剩余时间。
- 健康分级：
  - `online`：心跳正常，token 剩余 >1h
  - `expiring`：token 剩余 <1h（发事件，准备重登）
  - `degraded`：心跳连续失败但 token 未过期（降速、暂停路由）
  - `expired`：鉴权 -2 或 token 过期
  - `relogin_pending` / `manual_required`
- 请求池只路由到 `online/expiring`；`degraded` 降权；`expired` 不路由。

### 4.2 Token 生命周期实验（P2 必须做）

1. **是否滑动续期**：持续心跳下，观察 `expireTime` 是否变化（若变化 → 长期保活只需心跳）。
2. **旧 token 宽限**：重新登录后旧 token 是否仍可用、宽限多久（决定重登平滑切换策略）。
3. **并发登录**：同账号重复登录是否踢掉旧 token（多进程/多设备场景）。
4. **静默续期**：token 到期前页面是否自动调用刷新（监听网络）；若有隐藏接口 → 纳入保活。
实验产物写入 `docs/exploration`，并据此确定「心跳保活 vs 定时重登」比例。

### 4.3 到期前自动重登编排

- 触发：token 剩余 <45min 或心跳失败 → 进入 `relogin_pending`。
- 策略：
  1. 尝试 `silentRelogin`（同 profile 重走 OAuth；若可免扫码）；
  2. 失败 → 生成二维码并发布事件（WebUI/CLI/REST 可获取），通知管理员扫码；
  3. 扫码确认后自动接管（无需人工点页面）。
- **错峰**：所有账号的到期时间分散（登录时记录 expiresAt；重登任务按到期时间排序，平滑错开），避免同时掉线。
- 并发：全局重登并发 ≤2；同账号互斥。
- 失败升级：连续 2 次 silent 失败 → 必须人工；连续 3 次扫码失败 → 告警。

### 4.4 会话存储与恢复

- token 加密存储（AES-GCM，key 文件 600）；`sessions` 表含 expiresAt。
- **daemon 重启恢复**：token 未过期 → 直接 `online`（HTTP 可用，无需浏览器）。
- **浏览器进程无状态**：业务不依赖浏览器；只有登录/重登时才拉起浏览器（降低资源占用，利于 50 账号）。
- **profile 持久化**：每账号独立 profile（`~/.fuma-platform/profiles/<accountId>`），用于免扫码实验/扫码登录加速；profile 权限 600。
- 保活进程**不常驻浏览器（默认）**：按需启动（登录/重登/二维码刷新），完成后关闭；需要加速时可对个别账号开启 `keepBrowserAlive=true`（仅登录重登用，非保活前提）。

### 4.5 多账号场景（3–50）

- 登录/重登任务队列 + 并发限制（默认 2 个浏览器上下文）。
- 每账号独立限速（默认读写各 1–2 QPS），避免触发风控。
- 到期时间错峰：批量导入账号时按 30min 间隔分散首次登录；后续重登按到期时间自动错峰。
- 账号池健康视图：CLI/REST 可查（在线/剩余时长/最近心跳/容量）。

### 4.6 告警与运维

| 事件 | 通知方式 |
|---|---|
| 二维码就绪 / 需人工扫码 | 事件 + WebUI/CLI 提示 |
| 账号即将过期（<1h） | 事件（EMA 提醒） |
| 重登失败/需人工 | 事件 + 日志告警 |
| 心跳连续失败 | 事件（degraded） |
| 风控信号（滑块/安全验证） | 事件 + 冷却 + 告警 |

### 4.7 保活指标（可观测）

`session_health` 表 + 指标：在线率、平均心跳延迟、token 剩余分布、重登成功率/耗时、人工介入次数、扫码等待时长、silentRelogin 成功占比。

## 6. 登录失败矩阵

| 现象 | 判定 | 处理 |
|---|---|---|
| 二维码失效 | 页面提示/超时 | reload 重新生成，刷新计数+1 |
| 11041 长时间未确认 | 已扫未确认 | 提示用户确认；超时重发 |
| orgList 无目标组织 | 配置/账号组织变更 | failed（配置错误事件） |
| 企业列表无目标企业 | 权限/企业变更 | failed |
| 进入企业后要求钉钉二次验证 | 企业配置开启 | 复用二维码/账密模式 |
| token 鉴权 -2 | 会话失效 | expired → 重登 |
| 滑块连续拒绝 | 风控 | 冷却 10min+，告警 |
| 短信未送达 | 账密模式 | 降级为扫码模式 |

## 7. 安全

- token/profile 仅本地、加密、600；日志与事件脱敏。
- 登录浏览器 profile 与业务数据分离；profile 不跨账号共享。
- REST 仅 127.0.0.1；MCP 仅 stdio。
- 扫码是唯一人工环节：产品上明确提示，不做规避风控的对抗设计（遵守平台条款）。

## 8. 验收用例

1. 预启动后触发登录 → ≤5s 返回二维码 payload/base64；终端可渲染。
2. 扫码确认 → ≤8s 状态 online，token 加密落库，事件齐全。
3. 模拟 token 失效（改库）→ 状态 expired + 重登队列；silentRelogin 成功则≤15s 恢复。
4. 提前 45min 触发到期重登，账号不中断（旧 token 有效期内完成切换，验证旧 token 宽限）。
5. 3 账号并发重登：全局并发≤2，最终全部 online，无互相阻塞。
6. daemon 重启：未过期账号直接 online；过期账号进入重登队列。
7. 二维码过期连续 3 次 → 事件提示人工介入。

# 附：会话保活结论 v4（回答 D6，2026-11-14 23:40）

## 1. 先回答两个问题

### Q1：会话保活需要常驻浏览器吗？→ **不需要（保活用 HTTP 心跳即可）；浏览器只在登录/重登时有用**
- 业务接口全部是「token 注入的纯 HTTP」（已验证：客户/公海/查重/海关/监测均可在无浏览器下调用）。
- 因此只要 token 有效，心跳（如每 3–5min 调 `personalsettingGet`）就能“制造活动”，不需要浏览器进程。
- 浏览器常驻 **不能** 恢复 SPA 会话（实测：关闭进程后仅 cookies/storage 无法恢复，跳 `#/main/nopage`），所以“常驻浏览器=保活”是伪命题。
- 浏览器常驻的唯一价值：① 保持钉钉 OAuth 会话热态，提高「免扫码重登」成功率；② 重登/换码时零冷启动。属于**可选优化**，不是保活必需。

### Q2：会话能永久保活吗？→ **可能可以（取决于服务端是否按活动滑动续期），需要一次 24h 实验确认**
证据：
| 证据 | 结论 |
|---|---|
| token 对象 `createTime/expireTime` 固定 = 24h（实测） | token 本身 24h 硬过期 |
| bundle 中**没有** 孚盟 auth token 刷新/续期接口（`refreshToken` 仅是 Google Ads OAuth；`relogin` 仅是 WhatsApp WA；`expireTime` 仅是 OSS/STS token） | 前端无静默续期机制 |
| i18n 文案：`该账号24小时未操作，请重新登录` | **服务端会话很可能是“24h 无操作”语义（活动滑动续期）**，与 token 的固定 24h 不是同一回事 |
| i18n 文案：`该账号在异处登录，需确认是否为本人操作` | 多端登录触发安全确认，重登可能踢掉/需要确认 |

**假设**：服务端 session 以「最后活动时间 + 24h」过期，而 token 的 `expireTime` 只是签发字段。
- 若假设成立 → **心跳即可永久保活**（不重登、不需浏览器常驻），只需在 token 过期前通过心跳活动续住 session；但 token 字段仍可能被网关校验 → 必须实验。
- 若假设不成立 → token 24h 后一定 -2，只能**自动重登**（免扫码实验或人工扫码）。

## 2. P2 首日实验方案（24–30 小时，产出结论后再定保活架构）

| 实验 | 方法 | 判定 |
|---|---|---|
| E1 活动续期 | 测试账号每 3min 调 `personalsettingGet`，持续 26h，记录首次 `-2/未登录` 的时间与错误码/文案 | 26h 仍可用 → 活动可续期；24h 处失效 → token 硬过期 |
| E2 静默对照 | 另一测试账号不心跳，24h 后首次调用观察结果 | 确认空闲超时阈值 |
| E3 重登后旧 token | 到期后重新登录，用旧 token 调一次 | 旧 token 宽限期/是否立即失效 |
| E4 多端登录 | 同一账号二次登录后，旧会话是否被踢 | 决定“常驻浏览器+心跳”与重登冲突策略 |
| E5 免扫码重登 | 同 profile 重开钉钉 OAuth，观察是否直接进入组织选择/自动授权 | 决定自动重登能力 |

## 3. 保活架构结论（默认方案）

1. **不常驻浏览器**：daemon 启动、业务运行均无浏览器；仅在 `session.login/relogin/qr` 时拉起（配置 `login.keepBrowserAlive=false` 默认关闭）。
2. **HTTP 心跳保活**：每 3–5min 轻量探测；连续 3 次失败 → degraded 告警。
3. **到期兜底**：token 剩余 <45min 进入重登队列：
   - 若 E1 证明活动可续期 → 心跳维持即可，无需重登；
   - 若 24h 硬过期 → 先尝试 E5 免扫码静默重登；失败则发二维码事件等人工扫码（约每 24h/账号一次，除非逃逸成功）。
4. **常驻浏览器开关**：对“经常需要换码/重登”的账号可单独开启（`keepBrowserAlive=true`），仅作加速；不作为保活前提。
5. **指标**：在线率、首次 -2 时间、重登次数/耗时、人工扫码次数、心跳失败率。

- 发起新登录后，**旧的 accessToken 立刻失效**：观察器中旧账号 token（剩余 21h）在 00:34:21 心跳返回 `session_expired`。
- 影响：
  1. 重登应当「先完成新登录、再切换业务路由」，旧 token 不可并行使用；
  2. 多进程/多端同时登录会互相踢掉（与 i18n「该账号在异处登录」一致）；
  3. 平台不做多实例共享同一账号登录；同一账号登录必须串行（已有 busy 锁）。
- 24h 保活实验（E1）已在生产账号启动：`fuma-keepalive-prod.service`，每 5min 心跳，日志 `/tmp/fuma-prod-keepalive.jsonl`（另存 ~/.fuma-platform 下），观察 token 是否活动续期。

4. 空闲阈值（E2，多久无活动会真正过期）尚未测出：本实验空闲 7h15m 仍有效；待更长停机观察。
